# TailDesk Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.
> **Status:** DRAFT — design + phased plan. Not yet implemented.

**Goal:** Fork RustDesk into "TailDesk" — a remote-desktop client that connects
peer-to-peer over a Tailscale tailnet, with **no external RustDesk server
(hbbs/hbbr) required.**

**Architecture:** Keep all of RustDesk (screen capture, input injection, video
codec, Flutter UI). Surgically replace the *connection layer*: drop the
rendezvous/relay dependency, make the service hold a persistent inbound listener
on the tailnet, dial peers by MagicDNS hostname / 100.x IP, and replace hbbs's
"key vouching" with Tailscale identity + SSH-like key pinning.

**Tech Stack:** Rust (tokio, existing `hbb_common`), existing `scrap`/`enigo`/
`clipboard` libs, Flutter UI, Tailscale (MagicDNS + `tailscale status --json`
for discovery).

---

## 0. The big finding (read this first)

**You do NOT need to rebuild RustDesk.** The name "rebuild" is doing a lot of
work, and the code says otherwise.

RustDesk's value is in the *hard* parts: cross-platform screen capture, input
injection, H.264/VP9 video, audio, clipboard, and the Flutter UI. That is
thousands of lines of the most platform-specific code in the project (Wayland,
X11, macOS, Windows). Rebuilding *that* from scratch to "use Tailscale" would be
a monumental, pointless effort.

The part that actually needs to change is the **connection layer**, and it is
relatively self-contained. Even better: RustDesk *already has* a "dial a known
host, skip rendezvous" seam that we can build on. So TailDesk is a **surgical
fork**, not a rewrite, and the MVP is small.

### Verified facts (grounded in the code)

1. **Three connect paths today** (`src/client.rs`):
   - **Default = rendezvous + hole-punch** (`_start_inner`, line 371+): client
     dials hbbs (21116), sends `PunchHoleRequest`, hbbs replies
     `PunchHoleResponse` carrying the peer's public `socket_addr` (line 514) and
     hbbs-*vouched* public key `ph.pk` (line 512), then `Self::connect(...)`
     races direct TCP/UDP and falls back to hbbr relay (21117).
   - **LAN discovery, no hbbs** (`src/lan.rs`): UDP broadcast ping/pong →
     `LanPeers{id, ip_mac, hostname, username, platform, online}`. The existing
     pattern for "find peers without a server."
   - **Direct "connect to host:port"** (`_start`, ~line 258): if the peer string
     is an IP (`is_ip_str`) or `domain:port` (`is_domain_port_str`), it dials
     `connect_tcp_local(check_port(peer, RELAY_PORT + 1))` **directly** and
     returns `direct=true, signed_id_pk=None`, skipping rendezvous entirely.
     *This is our primary seam.*

2. **The secure handshake exists and is transport-independent, but it is
   gated by a `secure` flag — and the direct path disables it**
   (`src/server.rs:198` `create_tcp_connection`, `src/client.rs:766`
   `secure_connection`). When `secure=true` (the rendezvous/hole-punched path),
   the server sends `SignedId{id, pk}` signed by the device's long-term secret
   key, the client replies `PublicKey` and both call `set_key(...)` with a
   fresh forward-secret symmetric key (`create_symmetric_key_msg`). When
   `secure=false` (the direct path, `rendezvous_mediator.rs:900`), no keys are
   exchanged at all. So the *mechanism* is there for TailDesk to enable on the
   tailnet path; today it's simply turned off for direct connections (see
   fact 7).

3. **Identity is local, not server-derived** (`libs/hbb_common/src/config.rs`):
   `get_id()` → `gen_id()` → `get_auto_id()` (desktop) derives the ID **from the
   MAC address**; the keypair is generated locally (`get_key_pair`, line 1119).
   So a machine has a stable RustDesk identity *without* any server.

4. **`hbbs`/`hbbr` are a separate external repo** (`rustdesk/rustdesk-server`),
   not vendored here.

5. Ports (`libs/hbb_common/src/config.rs:123`): 21116 rendezvous, 21117 relay,
   21118 ws-rendezvous / **direct-access**, 21119 ws-relay.

6. **RustDesk already ships a persistent direct-access server** — the feature
   this plan initially assumed was the "one real gap." `src/rendezvous_mediator.rs:847`
   `direct_server()` runs from service startup (`start_all`, line 135), listens
   via `listen_any(port)` (default `RENDEZVOUS_PORT + 2` = **21118**, overridable
   with `direct-access-port`), and hands each inbound connection to
   `create_tcp_connection(..., secure=false)` (line 900). Gated by the
   `direct-server` option — **default OFF** (`option2bool`, `config.rs:2831`:
   `direct-server` is only true when `"Y"`). The client side already dials
   `check_port(peer, RELAY_PORT + 1)` = 21118 for a bare IP (the `is_ip_str`
   branch, `src/client.rs` `_start`) or any `domain:port` (`is_domain_port_str`).

7. **The direct path is unencrypted and unauthenticated at the protocol layer.**
   Server: `create_tcp_connection` is called with `secure=false` (no `SignedId`,
   no symmetric key). Client: `secure_connection` (`src/client.rs:766`) gets
   `signed_id_pk` empty on the direct path, sends one empty message, and
   returns `None` — no keys are set on the stream. So a stock direct connection
   is plaintext. On the tailnet, **WireGuard encrypts the whole flow**, so the
   wire is safe; but (a) peer identity is *not verified at all* (any host on the
   reachable network can be dialed, no key pinning), and (b) anyone who can see
   the local-network segment sees the RDP-like payload in the clear. **This is
   the piece TailDesk actually has to build: the key-pinning layer (Phase 2).**

## 1. The crux: trust model

This is the interesting part, and the part that actually needs a decision.

In stock RustDesk, the **server (hbbs) is the trust anchor**: it vouches for the
peer's public key, so the viewer can verify the peer's `SignedId`. No server,
no third party to vouch.

TailDesk replaces that with two layers:

- **Tailscale = network + coarse identity.** Tailscale already authenticates
  every node on the tailnet (control server / OIDC / auth keys). If you can open
  a TCP connection to a tailnet hostname, you've already been authenticated by
  the tailnet. The wire is WireGuard-encrypted end to end.
- **Key pinning = per-peer identity (SSH `known_hosts` model).** On first
  connect, the viewer shows the peer's key fingerprint and the user confirms;
  the fingerprint is pinned in the peer's saved config. Later connects verify
  against the pin; a mismatch warns/blocks. This preserves end-to-end identity
  trust with **zero** server. RustDesk already has the seam: `server.rs:239`
  `Config::set_key_confirmed(false)` / "Force to update pk".

**Net:** Tailscale answers *"is this a machine on my tailnet, and is the wire
safe"*; key pinning answers *"is this the specific machine I think it is."* The
existing RustDesk key exchange keeps giving per-session confidentiality.

This is a **defensible security model** and simpler than the status quo (it
removes a server that had to be kept patched and reachable).

**What it does NOT give you** (honest limits, for your governance hat):
- No central ACL / audit log out of the box (that was hbbs's job). If you want
  "who connected to what, when," you add it (Tailscale's own logs are a start;
  a local audit log is cheap).
- Tailscale's control server (or your `tailscaled` in self-hosted / Headscale
  mode) is now the identity authority. If you're a municipal CIO, note this:
  you can run **Headscale** (self-hosted Tailscale control plane) to keep that
  authority in-house.

## 2. Target architecture

```
        tailnet (WireGuard, MagicDNS)
┌──────────────────────────────────────────────┐
│  viewer (this machine)         target (remote) │
│  ┌──────────────┐              ┌──────────────┐│
│  │ TailDesk UI  │  host:21118  │ TailDesk svc ││
│  │  (Flutter)   │ ───────────► │  persistent  ││
│  │ dial tailnet │   WireGuard  │  TCP listener││
│  └──────┬───────┘              └──────┬───────┘│
│         │ SignedId/PublicKey key      │ accept ││
│         │ exchange + key pinning      │ _conn  ││
│         ▼                              ▼       ││
│      symmetric key set            Connection::start
└──────────────────────────────────────────────┘
   NO hbbs (21116). NO hbbr (21117). NO hole punching.
```

**What changes / is dropped:**

| Component | Stock RustDesk | TailDesk |
|---|---|---|
| hbbs rendezvous (21116) | required | **removed** (dead code on tailnet path) |
| hbbr relay (21117) | required | **removed** (tailnet = direct path) |
| hole-punching / NAT detection | required | **removed** (WireGuard does NAT traversal) |
| peer discovery | LAN UDP broadcast | **Tailscale** (`status --json` / MagicDNS) |
| service inbound listener | on-demand, post-rendezvous | **persistent** on tailnet port |
| key trust anchor | hbbs vouching | **Tailscale identity + key pinning** |
| capture / input / video / UI | — | **unchanged** |
| per-session encryption | key exchange on stream | **unchanged** |

## 3. Phased implementation

### Phase 0 — MVP: "type the address, it connects" (shrink-to-zero, then verify)

**Corrected from the initial draft.** Because RustDesk already ships the
persistent direct server (off by default) and the client direct-dial path,
Phase 0 is mostly *configuration and verification*, not new code.

- **T0.1** Verify out-of-the-box direct connect over the tailnet with **zero
  code changes** (the "boring proof").
- **T0.2** Tiny code: accept a bare MagicDNS hostname (no `:port`) as a dial
  target — the one real gap in the existing direct path.
- **T0.3** Decide the TailDesk default posture (direct-server on, etc.) as
  build-time/config defaults.

#### T0.1 — Zero-code verification (do this first, it's the whole point)

Prereqs: two Linux boxes on the same tailnet; stock RustDesk builds
(deb/rpm/AppImage from upstream, or a local `build.py`); Tailscale running on
both (`tailscale ping remote-host` works).

1. On the **target**: enable Direct Access in Settings (or set the option):
   `direct-server=Y`. (Option is default OFF — confirmed via
   `option2bool`, `libs/hbb_common/src/config.rs:2831`.) The service
   auto-restarts its listener; log line: `Direct server listening on ...`.
   Confirm `ss -ltnp | grep 21118` shows the rustdesk process.
2. On the **viewer**: type the target's **tailnet IP** (`100.x.y.z`) into the
   ID field and connect. The `is_ip_str` branch (`src/client.rs` `_start`)
   dials `100.x.y.z:21118` directly. Expect a desktop, target screen login
   prompt.
3. Repeat with `100.x.y.z:21118` explicit.
4. Confirm on both boxes: no hbbs/hbbr processes anywhere; the rendezvous
   mediator still tries to register with `rs-ny.rustdesk.com` (harmless,
   eventually gives up) — note this for T0.3.
5. Confirm the **expected weaknesses** so we know what Phase 2 must fix:
   the connection is plaintext at the protocol layer (WireGuard-only
   encryption) and there is no peer-identity check.

**Exit criteria:** two tailnet peers share a desktop with **no rustdesk-server
anywhere**, stock binary, zero code changes. If this works (it should), the
"rebuild" framing is dead and TailDesk is a small delta.

#### T0.2 — Bare MagicDNS hostname dialing (the only real Phase 0 code)

Problem: a bare `remote-host` (no port) matches neither `is_ip_str` nor
`is_domain_port_str`, so it falls through to rendezvous as if it were a
RustDesk ID. Tailnet users should be able to type just the hostname.

Files:
- Modify: `src/client.rs` `_start` (line ~250) — add a branch before
  `is_ip_str`, only when tailscale mode is on

```rust
// TailDesk: bare MagicDNS host or bare 100.x IP -> direct dial on the direct port.
if crate::taildesk::is_tailnet_peer(peer) {
    let target = crate::taildesk::tailscale_target(peer); // "host:21118"
    let stream = connect_tcp_local(target, None, CONNECT_TIMEOUT).await?;
    return Ok(((stream, true, None, None, "Tailnet"), (0, "".into()), false));
}
```

- Create: `src/taildesk.rs` (new module; `mod taildesk;` in `src/lib.rs`):

```rust
use hbb_common::config;

// Tailnet mode: on by default in the TailDesk fork.
pub fn enabled() -> bool {
    config::option2bool(
        "enable-tailnet",
        &config::Config::get_option("enable-tailnet"),
    )
}

pub fn is_tailnet_peer(peer: &str) -> bool {
    let p = peer.to_ascii_lowercase();
    p.starts_with("100.")
        || (p.contains('.')
            && !p.contains(':')
            && !p.chars().all(|c| c.is_ascii_digit()))
}

pub fn tailscale_target(peer: &str) -> String {
    if peer.contains(':') {
        peer.to_string()
    } else {
        format!("{}:{}", peer, crate::rendezvous_mediator::direct_access_port())
    }
}
```

- Expose `direct_access_port()` from `src/rendezvous_mediator.rs` (lift the
  existing private `get_direct_port()`, line 837, to `pub(crate)`).

This reuses the exact return shape the existing `is_ip_str` path uses, so
downstream code (login prompt, connection start) is untouched.

#### T0.3 — Fork default posture

- Add `enable-tailnet` option (default `Y` in the fork) + surface it in
  settings.
- In the fork's defaults, set `direct-server=Y` so the listener is always on
  (that is the whole point of the product).
- Optional (later, Phase 3): skip rendezvous registration entirely when
  `enable-tailnet=Y` and no custom server is configured, so logs stay clean
  and there's no outbound chatter to `rs-ny.rustdesk.com`.

**Phase 0 exit criteria:** bare-hostname connect works on the fork build;
out-of-the-box direct connect verified on stock (T0.1).

### Phase 1 — Encryption + key pinning (the actual work)

This is where TailDesk earns its security model. The stock direct path runs
with `secure=false` (no `SignedId`, no symmetric key — plaintext at protocol
layer). WireGuard covers the wire, but we want per-peer identity and defense
in depth:

- **T1.1** Turn on the existing key exchange for the direct path.
  - Server: in `direct_server` (`src/rendezvous_mediator.rs:847`), call
    `create_tcp_connection(..., secure=true, ...)` instead of `false`. The
    `secure=true` branch (line 208) already sends `SignedId{id, pk}` signed
    with the device key and does the symmetric-key setup.
  - Client: the direct branch must run `secure_connection` (today it returns
    the raw stream without it). `secure_connection` currently requires
    `signed_id_pk` (hbbs-vouched) to proceed — with none, it sends an empty
    message and skips keys. Extend it: when `enable-tailnet` and no vouched
    pk, accept the peer's `SignedId` **against a pinned fingerprint** instead
    of hbbs's signature (see T1.2).
- **T1.2** Key pinning (SSH `known_hosts` model).
  - Store per-peer fingerprint in the peer's saved config
    (`PeerConfig` in `libs/hbb_common/src/config.rs` — same store as the
    remembered password).
  - First connect: viewer shows fingerprint (SHA-256 of the peer's public
    key, same format RustDesk shows for device fingerprints in
    `libs/hbb_common/src/fingerprint.rs`), user confirms, pin is saved.
  - Later connects: mismatch → hard block + loud warning (reuse the
    `SOLVING_PK_MISMATCH` / `set_key_confirmed(false)` machinery from the
    rendezvous path).
  - Fingerprint shown **before** the login prompt, so the user confirms
    identity first, then types the password.
- **T1.3** Now that the stream has a symmetric key, the login password and
  all control/media traffic are encrypted end to end *and* the identity is
  pinned. WireGuard + this = the two-layer model from §1.

**Phase 1 exit criteria:** direct connects are encrypted at protocol layer;
first connect prompts for fingerprint; a changed peer key is blocked with a
visible warning; the stock rendezvous path is unaffected.

- **T2.1** Enumerate tailnet peers via `tailscale status --json` (shell out;

- **T2.2** Map to `config::DiscoveryPeer` (the same struct LAN discovery

- **T2.3** Periodic refresh (30s) + on tailnet change; clicking a peer dials

- **T2.4** (Nice to have) show the peer's RustDesk ID alongside the hostname
  once connected (the `SignedId` carries it), so the pin list and the ID are

**Phase 2 exit criteria:** peer list shows live tailnet machines by hostname;
clicking one connects.

### Phase 3 — Hardening, branding, packaging

- **T3.1** Optional **Headscale** note in docs (self-hosted control plane) for

- **T3.2** Optional local **audit log** (who connected when) — cheap, and it

- **T3.3** Branding: "TailDesk" name, icons, app ids, `build.py`/`fastlane`

  off-tailnet fallback (recommended — a machine that isn't on the shared

  Don't delete working code in a fork you may want to rebase.

## 6. Risks & open questions (your call)

1. **Fork vs. upstream.** A surgical fork will drift from upstream RustDesk
   releases. Do you want (a) a clean fork you maintain, or (b) a thin patch-set
   you rebase onto upstream each release? For a security tool you probably
   care about upstream CVE fixes, (b) is healthier but more work. **This is the
   biggest strategic decision — decide before Phase 0.**
2. **Identity authority.** Tailscale's default control server vs. self-hosted
   **Headscale**. For your role, Headscale keeps the identity authority
   in-house. Do you already run Headscale, or is that a new piece?
3. **Scope of "between computers."** Is this just your homelab tailnet, or do
   you see this as something with multiple *users/accounts* (the hbbs account
   system)? Phase 0-2 assume a single-owner tailnet. Multi-user/ACL is a larger
   lift (Phase 3.2 territory).
4. **Mobile.** RustDesk has iOS/Android clients. The Tailscale transport works
   the same (phones are on the tailnet too), but mobile discovery via
   `tailscale status --json` and key-pinning UX need their own pass. Defer to
   Phase 3+; Phase 0-2 are desktop.
5. **The direct listener is already `0.0.0.0`-bound.** `direct_server` uses
   `listen_any()`, so the 21118 port is reachable on *every* interface —
   tailnet *and* local LAN. On a tailnet that's gated by WireGuard; on the
   LAN it's a plaintext desktop endpoint (pre-Phase-1). Mitigations:
   (a) Phase 1 encryption + pinning closes the plaintext hole regardless of
   interface; (b) optionally bind the listener to the `tailscale0` address
   specifically (`tailscale ip -4`) instead of `listen_any`. Recommend (b) as
   a small hardening task in Phase 1.

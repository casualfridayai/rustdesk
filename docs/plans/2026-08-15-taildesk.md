# TailDesk Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.
> **Status:** DRAFT — design + phased plan. Not yet implemented.

**Goal:** Fork RustDesk into "TailDesk" — a remote-desktop client that connects
peer-to-peer over a Tailscale tailnet, with **no external RustDesk server
(hbbs/hbbr) required.**

**Architecture:** Keep all of RustDesk (screen capture, input injection, video
codec, Flutter UI). Surgically replace the *connection layer*: drop the
rendezvous/relay dependency, make the service hold a persistent inbound listener
on the tailnet, dial peers by MagicDNS hostname / 100.x IP, and replace hbbs's
"key vouching" with Tailscale identity + SSH-like key pinning.

**Tech Stack:** Rust (tokio, existing `hbb_common`), existing `scrap`/`enigo`/
`clipboard` libs, Flutter UI, Tailscale (MagicDNS + `tailscale status --json`
for discovery).

---

## 0. The big finding (read this first)

**You do NOT need to rebuild RustDesk.** The name "rebuild" is doing a lot of
work, and the code says otherwise.

RustDesk's value is in the *hard* parts: cross-platform screen capture, input
injection, H.264/VP9 video, audio, clipboard, and the Flutter UI. That is
thousands of lines of the most platform-specific code in the project (Wayland,
X11, macOS, Windows). Rebuilding *that* from scratch to "use Tailscale" would be
a monumental, pointless effort.

The part that actually needs to change is the **connection layer**, and it is
relatively self-contained. Even better: RustDesk *already has* a "dial a known
host, skip rendezvous" seam that we can build on. So TailDesk is a **surgical
fork**, not a rewrite, and the MVP is small.

### Verified facts (grounded in the code)

1. **Three connect paths today** (`src/client.rs`):
   - **Default = rendezvous + hole-punch** (`_start_inner`, line 371+): client
     dials hbbs (21116), sends `PunchHoleRequest`, hbbs replies
     `PunchHoleResponse` carrying the peer's public `socket_addr` (line 514) and
     hbbs-*vouched* public key `ph.pk` (line 512), then `Self::connect(...)`
     races direct TCP/UDP and falls back to hbbr relay (21117).
   - **LAN discovery, no hbbs** (`src/lan.rs`): UDP broadcast ping/pong →
     `LanPeers{id, ip_mac, hostname, username, platform, online}`. The existing
     pattern for "find peers without a server."
   - **Direct "connect to host:port"** (`_start`, ~line 258): if the peer string
     is an IP (`is_ip_str`) or `domain:port` (`is_domain_port_str`), it dials
     `connect_tcp_local(check_port(peer, RELAY_PORT + 1))` **directly** and
     returns `direct=true, signed_id_pk=None`, skipping rendezvous entirely.
     *This is our primary seam.*

2. **The secure handshake is transport-independent** (`src/server.rs:198`
   `create_tcp_connection`, `src/client.rs:780-830`). On the established `Stream`
   (however it was opened), the server sends `SignedId{id, pk}` signed by the
   device's long-term secret key, the client replies `PublicKey` and both call
   `set_key(...)` with a fresh forward-secret symmetric key (
   `create_symmetric_key_msg`). This gives **confidentiality** regardless of how
   the TCP connection was made. On the direct path the client has no hbbs-vouched
   `sign_pk`, so **identity is not verified** — that gap is exactly where key
   pinning goes.

3. **Identity is local, not server-derived** (`libs/hbb_common/src/config.rs`):
   `get_id()` → `gen_id()` → `get_auto_id()` (desktop) derives the ID **from the
   MAC address**; the keypair is generated locally (`get_key_pair`, line 1119).
   So a machine has a stable RustDesk identity *without* any server.

4. **`hbbs`/`hbbr` are a separate external repo** (`rustdesk/rustdesk-server`),
   not vendored here. The RustDesk *service* in this repo does **not** keep a
   persistent inbound listener — it only creates one on demand after rendezvous
   (`src/server.rs:181`, via `accept_connection`). **This is the one real gap for
   a serverless tailnet design: the service must listen permanently.**

5. Ports (`libs/hbb_common/src/config.rs:123`): 21116 rendezvous, 21117 relay,
   21118 ws-rendezvous, 21119 ws-relay. **21120 is free** → TailDesk direct port.

## 1. The crux: trust model

This is the interesting part, and the part that actually needs a decision.

In stock RustDesk, the **server (hbbs) is the trust anchor**: it vouches for the
peer's public key, so the viewer can verify the peer's `SignedId`. No server,
no third party to vouch.

TailDesk replaces that with two layers:

- **Tailscale = network + coarse identity.** Tailscale already authenticates
  every node on the tailnet (control server / OIDC / auth keys). If you can open
  a TCP connection to a tailnet hostname, you've already been authenticated by
  the tailnet. The wire is WireGuard-encrypted end to end.
- **Key pinning = per-peer identity (SSH `known_hosts` model).** On first
  connect, the viewer shows the peer's key fingerprint and the user confirms;
  the fingerprint is pinned in the peer's saved config. Later connects verify
  against the pin; a mismatch warns/blocks. This preserves end-to-end identity
  trust with **zero** server. RustDesk already has the seam: `server.rs:239`
  `Config::set_key_confirmed(false)` / "Force to update pk".

**Net:** Tailscale answers *"is this a machine on my tailnet, and is the wire
safe"*; key pinning answers *"is this the specific machine I think it is."* The
existing RustDesk key exchange keeps giving per-session confidentiality.

This is a **defensible security model** and simpler than the status quo (it
removes a server that had to be kept patched and reachable).

**What it does NOT give you** (honest limits, for your governance hat):
- No central ACL / audit log out of the box (that was hbbs's job). If you want
  "who connected to what, when," you add it (Tailscale's own logs are a start;
  a local audit log is cheap).
- Tailscale's control server (or your `tailscaled` in self-hosted / Headscale
  mode) is now the identity authority. If you're a municipal CIO, note this:
  you can run **Headscale** (self-hosted Tailscale control plane) to keep that
  authority in-house.

## 2. Target architecture

```
        tailnet (WireGuard, MagicDNS)
┌──────────────────────────────────────────────┐
│  viewer (this machine)         target (remote) │
│  ┌──────────────┐              ┌──────────────┐│
│  │ TailDesk UI  │  host:21120  │ TailDesk svc ││
│  │  (Flutter)   │ ───────────► │  persistent  ││
│  │ dial tailnet │   WireGuard  │  TCP listener││
│  └──────┬───────┘              └──────┬───────┘│
│         │ SignedId/PublicKey key      │ accept ││
│         │ exchange + key pinning      │ _conn  ││
│         ▼                              ▼       ││
│      symmetric key set            Connection::start
└──────────────────────────────────────────────┘
   NO hbbs (21116). NO hbbr (21117). NO hole punching.
```

**What changes / is dropped:**

| Component | Stock RustDesk | TailDesk |
|---|---|---|
| hbbs rendezvous (21116) | required | **removed** (dead code on tailnet path) |
| hbbr relay (21117) | required | **removed** (tailnet = direct path) |
| hole-punching / NAT detection | required | **removed** (WireGuard does NAT traversal) |
| peer discovery | LAN UDP broadcast | **Tailscale** (`status --json` / MagicDNS) |
| service inbound listener | on-demand, post-rendezvous | **persistent** on tailnet port |
| key trust anchor | hbbs vouching | **Tailscale identity + key pinning** |
| capture / input / video / UI | — | **unchanged** |
| per-session encryption | key exchange on stream | **unchanged** |

#### T0.2 — Service persistent listener (the real change)

Files:
- Create: `src/taildesk.rs` (new module; `mod taildesk;` in `src/lib.rs`)
- Modify: `src/core_main.rs` — start it when `use-tailscale` is on

This is the equivalent of what `accept_connection_` already does per-connection,
but as a long-lived loop. `create_tcp_connection` / `accept_connection` are the
existing entry points (`src/server.rs:198` / `275`).

```rust
// src/taildesk.rs
use crate::server::{accept_connection, ServerPtr};
use hbb_common::{log, tcp::new_listener, config, ResultType, Stream};
use std::net::SocketAddr;

/// Persistently listen on all interfaces (incl. tailscale0) for direct dials.
pub async fn start_listener(server: ServerPtr) -> ResultType<()> {
    let port = config::Config::tailscale_direct_port();
    let bind: SocketAddr = ([0, 0, 0, 0], port).into();
    let listener = new_listener(bind, true).await?;
    log::info!("TailDesk listener on {}", listener.local_addr()?);
    loop {
        // reuse the existing per-connection accept path; secure=true so the
        // SignedId/PublicKey key exchange still runs.
        match listener.accept().await {
            Ok((stream, addr)) => {
                stream.set_nodelay(true).ok();
                let stream = Stream::Tcp(
                    hbb_common::tcp::FramedStream::new(addr, None, 0).await?,
                );
                tokio::spawn(async move {
                    accept_connection(
                        server,
                        stream,
                        addr,
                        true, // secure
                        crate::rendezvous_mediator::connection_meta_default(),
                    )
                    .await;
                });
            }
            Err(e) => log::warn!("TailDesk accept: {}", e),
        }
    }
}
```

> Note: `connection_meta` in `src/rendezvous_mediator.rs:36` builds the
> `ConnectionMeta`. Expose a `_default()` variant (or inline an empty meta here)
> since a tailnet dial has no rendezvous context. Verify the exact fields the
> rest of `create_tcp_connection` needs and pass minimal sensible defaults
> (local, no relay, no punch). **Confirm the `FramedStream::new` signature
> against `libs/hbb_common/src/stream.rs` before implementing** — the exact
> constructor args may differ; the plan pins the *shape*, the implementer pins
> the exact call.

`is_tailnet_peer` / `tailscale_target` (in `src/taildesk.rs`):

```rust
pub fn is_tailnet_peer(peer: &str) -> bool {
    let p = peer.to_ascii_lowercase();
    // a 100.x tailnet IP (CGNAT 100.64.0.0/10), or a bare MagicDNS hostname
    // (no port, not a RustDesk numeric id).
    p.starts_with("100.") || (p.contains('.') && !p.ends_with(':') && !p.chars().all(|c| c.is_ascii_digit()))
}

pub fn tailscale_target(peer: &str) -> String {
    if peer.contains(':') { peer.to_string() }
    else { format!("{}:{}", peer, hbb_common::config::Config::tailscale_direct_port()) }
}
```

This reuses the exact `connect_tcp_local` + return-shape the existing
`is_ip_str` path already uses, so downstream code (key exchange, connection
start) is untouched.

### Phase 2 — Key pinning (the security layer)

- **T2.1** Store a per-peer key fingerprint in `PeerConfig` (the same store that
  holds the remembered password, `src/client.rs` `LocalConfig`/`PeerConfig`).
- **T2.2** On the direct-path `SignedId` verify (`src/client.rs:801`): if no
  pinned fingerprint for this peer → prompt user to confirm the fingerprint
  (first-connect), then pin it. If pinned and mismatched → warn + block
  (reuse the `set_key_confirmed(false)` / "pk mismatch" seam at
  `src/client.rs:810` and `src/server.rs:239`).
- **T2.3** A "known devices" view to inspect/forget pinned keys.

This is the piece that makes TailDesk *trustworthy* rather than just *convenient*.
Without it, anyone on the tailnet who spoofed a hostname could MITM the
identity (the wire is still WireGuard-encrypted, but the peer identity would be
unverified).

**Phase 2 exit criteria:** first connect prompts + pins; second connect is
silent; a key change triggers a visible warning.

## 6. Risks & open questions (your call)

1. **Fork vs. upstream.** A surgical fork will drift from upstream RustDesk
   releases. Do you want (a) a clean fork you maintain, or (b) a thin patch-set
   you rebase onto upstream each release? For a security tool you probably
   care about upstream CVE fixes, (b) is healthier but more work. **This is the
   biggest strategic decision — decide before Phase 0.**
2. **Identity authority.** Tailscale's default control server vs. self-hosted
   **Headscale**. For your role, Headscale keeps the identity authority
   in-house. Do you already run Headscale, or is that a new piece?
3. **Scope of "between computers."** Is this just your homelab tailnet, or do
   you see this as something with multiple *users/accounts* (the hbbs account
   system)? Phase 0-2 assume a single-owner tailnet. Multi-user/ACL is a larger
   lift (Phase 3.2 territory).
4. **Mobile.** RustDesk has iOS/Android clients. The Tailscale transport works
   the same (phones are on the tailnet too), but mobile discovery via
   `tailscale status --json` and key-pinning UX need their own pass. Defer to
   Phase 3+; Phase 0-2 are desktop.
5. **The persistent listener** is the one genuinely new surface area. Binding
   `0.0.0.0:21120` means *any* interface can reach it — on a tailnet that's
   fine (WireGuard gates it), but if a machine is on both the tailnet and an
   untrusted LAN, the service port is reachable on the LAN too. Mitigation:
   bind to the `tailscale0` interface address specifically instead of
   `0.0.0.0`. **Recommend binding to the tailscale0 IP** (discoverable via
   `tailscale ip -4`) — tighter, and it's the secure default.
